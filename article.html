Your roleplay character keeps repeating itself — how to tell whether it's the preset or the model

A five-minute, offline way to separate a prompt problem, a parameter problem and a model problem. No model calls, no signup.

People pour hours into a character card, get three great scenes, and then the character turns into a broken record: the same compliment, the same half-sentence ending in *smiles softly*, the same gesture narrated twice. The usual advice is "turn temperature up" (makes it worse) or "you need to fine-tune a LoRA" (costs money, and often fixes nothing, because the actual problem was a 150-token reply cap).

I built a small offline checker for exactly this. It reads a SillyTavern JSONL export and prints what is measurable, with the exact message index and the original sentence as evidence. No model calls, no signup on the landing page. Below is the reasoning, the traps I had to back out of, and a link at the end.

1. "Repetition" is at least five different failures

They look identical to a human reading a chat, and they have opposite fixes:

What you seeWhat it actually measuresUsual real fix
Same stock phrases (smirk, 若有所思, 挑眉)fixed-expression hit rate over a wordlistpersona/system prompt, or frequency penalty
Every reply opens the same wayopening n-gram homogeneityprompt for variation, not temperature
Replies slowly shrink and end mid-sentencelength drift vs max_tokens (tokens estimated, not characters)raise the cap, it is not the model
Model answers its own question, or writes your lineself-continuation runs; "steals the user's turn"stop sequences, prompt structure
Model re-narrates the setting you already knowtopic anchoringa genuinely hard semantic problem, mostly *not* solvable with wordlists

Notice the third row: a 110-token cap on a model asked for a two-paragraph reply produces something that looks exactly like "the model got lazy". People spend money on training before checking a number that is printed in their own preset file.

2. Measure first, and print the denominator

The single most common way a diagnostic tool lies to its user is quietly reading half the file and then reporting "no problems found". Twice now, a real customer record in a slightly different format (role/content instead of mes/is_user) produced a report with zero findings, because the parser skipped the lines it did not recognise and the ratio section then divided by a silently reduced denominator.

So the report starts with a reading line:

```

读数：文件里 44 行（含设置头 1 行）→ 读到 38 条消息；读不出 6 行（格式不认识 6 / 正文空 0 / 不是 JSON 0）

```

and if nothing was readable, the report says so in the first sentence instead of printing an empty finding list. Severity and finding counts are computed in one place, so "0 problems" can never appear next to "no model replies found" — that contradiction was a real bug reported by a user.

3. Say what you did not measure

A chat-only export contains no character card and no generation settings. Card-class checks (no example dialogue, card too thin, missing system prompt) and sampling-parameter checks (temperature, penalties, length cap) are then not testable — which is not the same as "fine". The report says this explicitly:

材料：本单没有角色卡、也没有预设文件 —— 卡片类与采样参数类此项未测：不是没问题，是没材料可看。

Same for checks we decided not to ship. Two examples, with the numbers, because "we don't check X" without data is indistinguishable from laziness:

  • Refusals that dodge the question. A human labelled 139 real replies: 6 genuine cases, all on one character. Three wordlist versions reached at best 4/6 recall with a 7% hit rate against a 4.3% true base rate — more noise than signal. Not shipped. What is shipped is a three-step manual review checklist.
  • The "always agrees with you" syndrome. 179 model replies, 5 agreeable openers, all of them legitimate in context. Not shipped; the report states the base rate instead of pretending the check exists.

4. Never green-light training without a baseline

The tool's verdict line has three states, and one hard rule: without a before/after baseline on the *same* scene, it never says "you can start LoRA evaluation". It says 证据不足，先别训 and then names what is missing. If a parameter is out of range it says 还差一步，先别训 and points at the parameter. Saying "train it" is the one answer that costs the user money and can be wrong for reasons the tool cannot see.
